# XLS DE10 architecture

## Repository boundaries

Authored code lives in `hardware/` and `software/`; shared glue and platform boundaries have colocated tests. `verification/` contains integration tests and fixtures. `vendor/` owns dependency provenance; `environment/` owns toolchain definitions. Commands are grouped under `workflows/` and `diagnostics/`. Generated RTL/Qsys and private Quartus projects live under `build/`. Historical `output/` evidence remains preserved. The pinned MiSTer framework is clean; the rejected scaler patch exists only in archived experiments. See [docs/ORGANIZATION.md](docs/ORGANIZATION.md) for migration limits.

## Build and integration

`hardware/renderer/dslx/core_sim.x` implements the hosted rendering core. `workflows/build/generate-xls-rtl --de10-proc` generates `build/generated/xls/work/core_sim_de10_rtl/CoreSimDe10.sv`; `workflows/build/quartus-compat-xls-rtl` lowers selected FIFOs without changing their handshake or capacity. The direct-scanout candidate retains the hardware-demo three-stage baseline/controller and four-stage texture-request actor. Wide DE10 context/cache/read FIFOs and palette pending data use registered-pop RAM outputs, removing duplicate forwarding registers without reducing capacity; the rejected two-stage controller failed physical timing. Saturated interpolated color channels are eight bits, and wide pixel context travels through a separate depth-eight M10K-backed FIFO. `workflows/build/select-xls-pipeline-stage` checks identical actor interfaces before selecting compiler-generated module bodies; alternate schedules/block IR are retained next to the baseline. No actor arithmetic is hand-rewritten by this selection.

`hardware/shared/rtl/XlsDe10Top.sv` connects the generated core to MMIO, texture-tag and palette memories, packed texture banks, framebuffer read/prefetch/write adapters, Avalon memory masters, and scanout. SpinalHDL-generated adapter RTL remains under `build/generated/scala/de10/`.

The former SpinalHDL renderer, CoreSim/CoreDe10 wrappers, renderer-only utilities, and their tests have been removed. Retained Scala implements XLS Avalon transfers, framebuffer scanout/prefetch, the BMB-to-Avalon bridge, HDMI timing/diagnostics, and the standalone DDR benchmark. `Config` now contains only scanout memory parameters; framebuffer read bundles live with `FramebufferPlaneReader`. MiSTer host-control work remains separate from the validated DE10 integration.

`de10/rtl`, `de10/bitstream`, and `de10/setup/program` select XLS. The base Quartus project and `De10Top` module name remain for the DDR benchmark and shared board assignments, not a second renderer. Hosted Glide supports XLS and trace capture; `verification/integration/trace_test.cpp` uses the existing XLS socket bridge when not run with `--ref-only`.

The pixel path separates interpolation, texture sampling/cache lookup, framebuffer reads, pixel processing, posted writes, and retirement with handshaked channels. Cache-fill completion and pixel retirement are distinct acknowledgments.

## MiSTer integration

The experimental computer lifecycle uses `software/runtime/mister/main_reset_broker.py`, not a Main patch or a polling-only watcher. Its exact-version manifest checks the stock Main and five pre-control instruction boundaries; ARM hardware execution breakpoints cover traced threads and fork/exec replacements. Native OSD departure/reboot waits for owned DOSBox's ordered GPU fence, runtime release, explicit retirement receipt, pipe EOF and successful exit. EXITKILL and guest parent-death SIGKILL contain broker crashes; these are not graceful flush receipts. `computer_service.py` guards boot startup, detects surviving mapped clients and bounds recovery to recognized hash-checked cores. Explicit service stops use pidfds and process birth identity, with no forced shutdown on timeout. Alternate programmers and arbitrary binaries are outside this mechanism's coverage.

`computer_launch.py` snapshots a validated saved JSON profile before generating DOSBox configuration. Fresh installation uses the stock user-startup hook and native Scripts profile selectors, preserving Main/kernel and refusing pre-existing targets. Native entry/profile selection/departure, cold reboot, boot enrollment and real-process crash recovery are board-tested. Media default to read-only; frozen runtime09 supports explicitly writable raw floppy/HDD copies through checked DOSBox media cleanup and exclusive image leases. Durable dirty markers refuse reuse after crashes, including read-only reuse after reboot. The supervising launcher retains ownership until the child sends its checked MEDIAOK receipt, exits successfully and closes the receipt pipe; it syncs the image and recovery directory before forwarding RETIRED to the unchanged broker. Maintained source integration checks seek/write/flush/sync/close errors and drains guest file buffers before drive teardown; a one-shot exit handoff prevents cleanup callbacks from throwing exit again. Disposable floppy/HDD write/restart tests, open-file native departure, native cold-reboot persistence and actual broker-crash gates pass on the matching candidate. Directory/ISO/VHD writes, hot eject, automatic repair and power-loss atomicity remain outside this path. Native Scripts provides a terminal editor for saved profile/CPU/memory/sound/media settings, using the same validated JSON snapshots rather than an in-core hot-mount editor. Copied-game initialization and stale-display behavior remain under investigation; these lifecycle tests do not establish new general-game or heavy-render retirement acceptance. See [machine profiles](docs/MISTER_MACHINE_PROFILES.md) and the experiment journal for candidate/deployment identities.

`hardware/platforms/mister/scala` contains framebuffer publication, keyboard state, a shared-DDR command mailbox, the 32-to-64-bit Avalon adapter, and a round-robin DDR arbiter with a configurable ordered read-route FIFO, eight entries by default. A separate two-entry size variant retains all eight platform clients: six renderer masters, local scanout and the mailbox. The arbiter permits independent commands while prior reads drain, preserves response ownership under backpressure, and bounds outstanding responses to 1024 beats. Selected writes do not require a free read-route slot. Reset drains every accepted beat before resetting the clients. This pipelined variant passes simulation but remains experimental pending complete physical timing signoff; the preserved signed cores retain the earlier single-flight arbiter. `MisterPlatform` connects six XLS renderer memory masters, the mailbox and local `MisterScanout`. The renderer's internal scanout is disabled for MiSTer only. Local scanout reads host slots or validated 640×480 RGB565 renderer buffers, drains accepted DDR responses before publishing a new descriptor, and sends RGB through an asynchronous pixel FIFO to the unchanged framework's video input (`FB_EN=0`). `MisterCore` wraps the platform in a DDR-draining reset boundary and synchronizes pixel reset. `workflows/build/prepare-mister-project` snapshots local RTL, constraints and CDC reporting into a separate Quartus project without changing pinned framework sources. The lean build uses upstream switches to omit unused ALSA audio and adaptive filtering and select nearest-neighbor downscaling; the demonstrated 640×480-to-720p path is upscaling. Normal HDMI scaling and all timing constraints remain enabled.

`MisterRtlGen` emits privately namespaced RTL; `workflows/check/check-mister-platform` checks shell elaboration/lint and integrated platform/C transport simulation. Frame acknowledgment now retires local reads of the previous slot, not the framework's internal scaler buffers. A slot remains unavailable if the new descriptor selects that same slot. The shared process-local runtime disables any previous presentation before its first copy, rotates non-active slots under one lock, and prevents further copies after a publication fault. It requires the reserved-memory ownership gate, accepting either an explicit no-map DT node or the verified stock MiSTer 511 MiB Linux-RAM limit with a matching physical DDR map and no overlapping resources. `/dev/mem` remains O_SYNC and exclusively locked; barriers alone do not establish uncached mappings. Only the selected custom core may use its upper-32-MiB window.

The host transport can leave one validated write-only batch in flight while the CPU prepares subsequent commands. No worker thread or FPGA protocol change is involved. Before reusing mailbox memory, any later submission or synchronous exchange drains and checks the previous acknowledgment under the mailbox lock. Reads, frame publication, direct renderer mapping and runtime release preserve ordering; asynchronous failures latch and prevent subsequent publication/reuse. The batch deadline starts before its initial copy and is not renewed by a delayed drain. Pending acknowledgments are polled up to eight times between monotonic-clock checks, reducing clock-call overhead while retaining timeout and sleep error handling. The existing synchronous exchange API still waits for completion. The shared runtime elides exact repeated full-word float-parameter writes at `0x88..0xfc`, retaining every triangle command and invalidating its parameter cache on other register writes, partial masks, synchronous write batches, failed write submissions and fresh acquisition. Integer aliases and read-modify-write paths therefore cannot leave cached float state stale. Generic mailbox exchanges still execute every submitted command.

### Host presentation

DOSBox's surface/input adapters and the X11-free Glide library share `libmister_runtime.so`. DOSBox and smaller Glide resolutions convert to fixed 640×480 RGB565 host slots; larger hardware descriptors are cropped by local scanout. At 640×480, Glide fences rendering, derives the displayed buffer and stride from GPU registers, and publishes renderer memory without CPU readback/copy. Swap waits for old-buffer DDR retirement before back-buffer reuse; Glide close disables direct scanout, and initialization retires stale descriptors before GPU memory initialization. Pending swaps and overlapping/out-of-range renderer layouts fail closed. DOSBox uses only Main's keyboard snapshot and suppresses its 2D presenter while Glide is enabled.

### Guest LFB and textures

Guest LFB accesses retain checked page-handler bounds and native ownership, not simulation shadow pointers. Eligible writes drain prior GPU framebuffer traffic and use the reserved renderer mapping, translating PCI rows to physical stride. Read/unlock replays the final masked write through the mailbox to invalidate GPU framebuffer caches; unsupported direct-write layouts retain the checked bus path. Full LFB policy acquires a companion write lock for legacy read-lock pointers; raw access policy, native lock ownership and extent checks remain enforced. Cached pointer accesses after guest unlock lazily reacquire native ownership, with implicit locks retired before each Glide API call and mappings revoked on screen disable. Front write locks retire scanout and republish on unlock; RGB565/ZA16 and upper/lower origins are supported without the pixel pipeline. The core retains `lfbMode` separately and routes auxiliary/origin-adjusted accesses. MiSTer Glide initializes the known single-TMU capacity and framebuffer geometry and sends only actual texture writes through the batched transport, avoiding dirty-page padding corruption. It omits obsolete SST PCI packer workaround writes, including tagged triangle-data-list entries, while retaining real texture writes and ordering barriers. The extended real-Glide RTL test includes guest LFB and paletted texture rendering; physical game validation remains separate. The isolated ARM shell supplies pinned dependencies. Runtime packaging includes a private loader/library directory, source archives and license/derivation inventory.

Signed-core timing and bounded live-game evidence are indexed in
`output/mister/game-fixes/evidence.json` and [the experiment journal](docs/SCREAMER2_EXPERIMENT_JOURNAL.md).
These tests do not establish whole-game performance or general game compatibility.

Upstream framework/Main/DOSBox-X revisions are pinned in `vendor/sources.json`; `workflows/build/prepare-mister-sources` verifies them without overwriting modified sources. Operating/build instructions and memory contracts are in [docs/MISTER.md](docs/MISTER.md). Historical decisions, waivers and acceptance results stay in the experiment journal.

The experimental scanout response stage registers DDR data and valid before the words FIFO, retaining each beat in the outstanding count until FIFO acceptance. This preserves reserved burst capacity and prevents early descriptor retirement. The physical candidate failed timing and is not deployed; results remain in the experiment journal.

## Experimental banked palette

The current un-deployed size-reduced candidate provides 16 RGB24 palette banks through `XlsPaletteMemory`. Exact MMIO address `0x3ec` reads capability `0x50414c10`; full-word writes select bank 0–15 through the controller's ordered command path. The external palette channel is 33 bits: bit32 marks selection, otherwise the existing index/RGB encoding is retained. Reset selects bank0; accepted read responses retain their captured data under backpressure.

MiSTer Glide flushes preceding commands before its shared-runtime palette API. Under the runtime lock, complete RGB tables use an exact-match MRU cache bounded by the advertised 16- or 32-bank capability; partial tables retain ordinary writes. Generic palette/selector writes, failed submissions and fresh acquisition invalidate relevant cached state. Old cores without the capability retain full uploads. The banked-palette candidates remain undeployed after physical timing failures;
live-game benefit is unproven. Candidate identities, ownership and measurements
remain in [the journal](docs/SCREAMER2_EXPERIMENT_JOURNAL.md).

## Texture cache

The primary cache retains 64 hashed 256-byte line identities; the shadow cache retains 16. Bank read bit 12 selects primary storage. Bank write bit 16 duplicates a write into primary and shadow storage, with shadow-set bits 12–15. Sectoring does not change these address fields or physical bank capacity.

The DE10 specialization enables two 128-byte sectors per line. `texture_cache::SECTOR_WORDS` is 32 and also configures `de10_adapter::block_read_transfer_adapter`, keeping the issued DDR word count and consumed fill length identical. The default non-sector specialization and block-read adapter still use full 64-word fills for existing non-DE10 paths and fixtures.

Sector-valid masks distinguish fetched portions of a line. Four per-request primary-tag snapshots track tag ownership through colliding tap allocations, avoiding a duplicate 64-entry primary-tag register array. Shadow metadata is maintained separately. A replacement tag or invalidated line discards the old sector mask.

Fills encode even/odd texels into both row-bank copies. For eight-bit textures, the two texel bytes in each bank word are expanded to the existing 16-bit texel representation. For sixteen-bit textures, the selected halfword occupies the valid lower half of each corresponding bank word. This representation is independent of texture layout, so layout-only changes need not invalidate cached data. Eight/sixteen-bit format changes, explicit invalidation, texture writes, and existing invalidating narrow requests still invalidate the cache.

A sector may be allocated before all of its words are written. Generation-tagged progress is emitted only after bank-write acknowledgment; the existing fill-prefix checks prevent reads of unwritten words. Prefetched DDR data alone does not establish a completed cache fill.

## Validation and timing

Use `nix develop` for DSLX tests, RTL generation, Verilator, and lint. `make -C hardware/renderer test`, `workflows/check/check-de10-xls-rtl`, and `workflows/check/check-de10-xls-replay` cover the principal XLS paths. The replay harness preserves the original 64-word counter fixtures and selects separate 32-word fixtures only when that refill size is observed; pixel/hash/completion checks remain mandatory.

Presented framebuffer and full 4 MB replay comparisons are separate from timing and throughput measurements. A simulation speedup is not a live-game FPS result. Experimental evidence and immutable signed-candidate manifests are kept under `output/de10/screamer2-17fps/`.

Quartus requires `nix develop --command devenv shell -- ...`. Every complete compile plus required timing signoff is bounded to 900 seconds; release candidates must pass the 50 MHz all-corner and vendor-DDR checks. The initial stock MiSTer synthetic demo used an explicit user waiver for small HDMI setup violations; the final direct-scanout build passes without that waiver. Board replay uses `--fb-base 0x3f400000`; RAM-only programming must preserve the protected runtime and persistent firmware policy.
